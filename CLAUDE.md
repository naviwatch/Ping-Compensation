# Ping Compensation

The Ping Compensation mod for Vermintide 2. This folder is its own git repo, cloned into Vermintide Mod Builder's (VMB) `mods` folder as `Ping Compensation`: the folder name must match `Ping Compensation.mod`, or VMB can't build it. If your VMB folder has its own `CLAUDE.md`, two levels up, its rules apply here too: if they aren't in your context, read that file before doing anything else.

## Design (keep this current)
The full design, its numbered decisions, the roadmap and the deferred work are in [Docs/Briefs/client-authoritative-melee.md](Docs/Briefs/client-authoritative-melee.md). Read it before changing anything. The tester handout is [Docs/Briefs/playtest-handout.md](Docs/Briefs/playtest-handout.md); update it whenever a build changes what testers see or should test. Testers get it as a PDF, so rebuild `Docs/Briefs/playtest-handout.pdf` with `handout_pdf.bat` after every change to it.

- Goal: client-authoritative enemy melee, and the player's own effect on enemies shown on their own screen at once. A swing aimed at a remote player is judged on that player's own screen, on the frame their copy of the enemy fires the damage animation event, from their live position, block and dodge. What the player's own hits and blocks do to an enemy is decided on their screen too. The host books whatever the client reports and never second-guesses it. It is PvE, so game feel beats fairness.

- Runs on: both.
  - Host (`Host.lua`): announces each swing to its target when the attack starts, with the crowd scaling of its damage, skips its own hit test at its damage frame, and books the client's answer. A hit is booked with `AiUtils.damage_target`, so the unmodified damage code still runs. A block is shown to the other players and makes the enemy recoil. A frenzy combo (family B) announces every step as its own swing (from `BTComboAttackAction._start_attack`), with the step's name; a step's hit is booked with the step's own damage and marks the step as landed, and a blocked step gets no recoil (as in vanilla) but is marked blocked, which can cut it short (`block_interrupts`) and changes its next step. Both only while the enemy is still in that step (`in_combo_step`). D15: where a step's next step depends on whether it landed or was blocked (two plague monk steps), the host holds the end of the step's animation (it hides `attack_finished` from `BTComboAttackAction.run`) until the answer arrives, for at most `pc.COMBO_WAIT` (0.5 s), then goes with what it would have judged itself; `/pingcomp combowait off` goes with that guess at once. An elite's sweep or overhead (family C, from `BTStormVerminAttackAction.enter`, announced with the attack animation the host noted, since the node doesn't write it to the blackboard) goes to every modded player, wherever they are, each as a swing of their own, with `aimed` true only for the player it attacks; each player's own screen judges whether the box reaches them, so the host never judges a modded player's part in a sweep (D50). At its damage frame the host runs the box overlap itself for its log, then lets vanilla run with the players it sent the swing to left out of the box's overlap (the `PhysicsWorld.immediate_overlap` hook, for the one call with `filter_player_hit_box_check`), so it still hits everyone else. Each answer is booked as vanilla's box test would for that player (`book_box`): the damage, or the blocked damage after `book_block`, the guard-break line, the catapult (`BTStormVerminAttackAction.catapult_enemy`) and the push. An elite's shove (family D, from `BTStormVerminPushAction.enter`) has its hit test switched off at `anim_cb_stormvermin_push` like family A's at `check_distance`; a hit books the damage, the pushed state and the knockback along the enemy's facing (`book_shove`).
  - Host (`Host.lua`, family F, D52): a disabler's hook, grab or pounce is announced after its node's `enter`, with its kind (`hook`, `grab`, `pounce`) in `step_name`; the hook and the grab go to their target, a pounce to every modded player, `aimed` for its target, because the sphere round the gutter runner's neck catches any player it flies into. The host's own test leaves modded players out: the hook's damage frame (the generic `anim_cb_damage`, whose target is `drag_target_unit`) goes through `check_distance` as family A's does; the leech's `overlap_players` doesn't run for a modded target, and the host only notes when its own projectile arrived; the leap's sphere (`check_colliding_players`) leaves modded players out through the overlap hook family C uses (`host.leap_skip`), and the leap never snaps at a modded target (`jump_data.snap_failed`). While an answer is due, the packmaster's attack doesn't time out (`attack_time_ends`), the leech's doesn't end with its animation (`attack_finished`) and the leap doesn't end on landing (`land_time`), each for at most `pc.GRAB_WAIT` (0.5 s) after the host's own moment. A hit is booked only while the special is alive, not staggered, still in that attack, and the player is one the game's own filter would take (`book_disabler` with `AiUtils.is_of_interest_to_packmaster`, `_corruptor` or `_gutter_runner`, the last knowing whom another special has disabled; the pin node itself would take a downed player, D57 review): the hook sets `attack_success`, so the pull follows; the grab sets `grabbed_unit` and `attack_success`, so `run` grabs; the pounce makes the next `BTCrazyJumpAction.run` return `done` with the player as `jump_data.target_unit`, so vanilla's `BTTargetPouncedAction` teleports the gutter runner onto them and pins them. Booked or refused, the client is told (`pc_reaction_ack`, kind `grab`).
  - Host (`HostReactions.lua`): applies the reactions a client decided. For every hit a modded client sends (melee, pushes, ranged, career skills) on an enemy in `pc.REACTION_BREEDS` (slave rats, clan rats and marauders with or without shields, fanatics, gors, ungors, plague monks, savages, stormvermin with or without shields and their patrols, maulers, Chaos warriors, bestigors, standard bearers; not bulwarks, T14), it books the damage as usual but skips its own stagger, and applies the client's `pc_stagger` (or a `pc_blast_staggers` entry) instead, with the client's animation (from any of that enemy's stagger lists) and facing, even mid-frenzy (D41). For a hit taken on a shield it still records the block on the shield, as the skipped stagger maths would have. A client's stagger ends one round trip early (D32): the host plays it faster through the `stagger_scale` animation variable, up to `pc.MAX_STAGGER_SPEEDUP` (3×, D38), and past that ends it early on its timer. It plays faster only the covered enemies in `pc.STAGGER_SCALE_BREEDS` (slave rats, clan rats, shielded clan rats, plague monks, ungors), whose stagger animations follow the variable (the calibration probe, D47). Every other covered enemy's (marauders with or without shields, fanatics, savages, gors, shielded stormvermin), whose animations ignore it, it ends early on its timer (D42, D47), and their lengths are measured at normal speed on both sides (`pc.stagger_speed`). The ungor's stagger action doesn't set `scale_animation_speeds`, so the host sets it for the length of `BTStaggerAction.enter` and then puts it back, with a plain `pcall` so it can't stay on the game's table: every ungor stagger then goes out with the variable, the faster speed for a client's, 1 for the host's own, so a faster value never lingers; clients play their own ungor staggers with it too. Its timer is shortened by the round trip as well. When a sped-up stagger reaches its end cue, the host works out the speed the animation really reached from the time it took (`host stagger=… speed asked=… reached=…`), counts the ones under 90% of the speed asked as slow, and doesn't learn a length from those. The animation lengths this needs come from `Timings.lua` (see below); a stagger whose animation has no length yet only gets its timer shortened. A recoil after a client's block plays the animation the client chose. Both start where the client saw the enemy: the host moves its copy there first if that is within 2.5 m, on the navmesh and on the same floor (D27). A predicted recoil ends one ping early (D14): like vanilla it waits for both its timer and its animation's cue (`anim_cb_blocked_cooldown`), or ends at once when the animation's `anim_cb_stunned_finished` clears `blackboard.blocked` (the savage's recoils), but these are counted from the host's own damage frame. The cue times come from `Timings.lua`, looked up by the recoil animation and the attack it interrupted (D43). Once the cue is known, its flag is held off until that time, whatever set it, and set then. Once the stunned cue is known, the animation's own is held back from vanilla until that time, when the host clears `blackboard.blocked` itself, and the animation's own late one is then dropped, so it can't end the next recoil. Until a cue is known, the host waits for the animation's own. Only `BTBlockedAction.leave` clears the cooldown flag, and a recoil ended before its animation's cue still gets that cue afterwards, so at the start of every recoil, of any enemy, a flag left over from an earlier one is cleared. The host measures both cues' times only from its own recoils, which start at the damage frame as in vanilla, and for those it makes vanilla's random animation pick itself so it knows which one plays. A recoil being watched for its cue stops being watched when any recoil or stagger of that enemy begins (in 2.2 a watch left over from a recoil cut short timed a later recoil's cue from the older one's start, 1.2 to 2.35 s instead of 0.95 s for marauders). A client's recoil isn't measured on the host; clients measure their own. If a client says its hit killed (`pc_kill`) and the enemy is still alive here 0.15 s later, the host kills it, credited to that player. Every predicted stagger and recoil is acknowledged (`pc_reaction_ack`). A client's stagger that ends a recoil takes the stagger count the recoil's `leave` left (it raises the count to 3 before the stagger's `enter`, `bt_blocked_action.lua:64`), so it isn't taken for someone else's and refused (D57 review). A stagger the enemy's own code has put on its timer alone (the savage's and the plague monk's after a broken frenzy, `stagger_ignore_anim_cb`) only has that timer brought forward, by the whole lead, without the animation's length. A client's report of a stagger the game refused on its screen (`pc_stagger` with an empty animation) only runs the hit's on-stagger procs, and so does a client's stagger `AiUtils.stagger` refuses here, as vanilla's `stagger_ai` runs them either way (`damage_utils.lua:3639`). A client's stagger on a globadier whose detonation has begun (`blackboard.suicide_run.explosion_started`) is acknowledged at once, not in `BTStaggerAction.enter`: the behaviour tree's first branch (`BTGlobadierSuicideStaggerAction`) takes it instead and kills the globadier with no killer, which sets off its gas, as in vanilla (`host stagger=… its detonation had begun`). With the debug log on, the host logs: a stagger it skipped for a client's hit that no client stagger or kill followed within a second (three for a blast's), where one that arrived up to a second before the host's own hit or blast counts too (a bomb's staggers can beat the host's copy of the bomb); why every recoil a client's block caused ended (`host swing=… recoil=… ended: …`, from `BTBlockedAction.leave`: its timer and cue, a stagger and whose hit it was, death, or another branch of the behaviour tree), with the blocked attack's animation and its timer and cue; and, for a client's hits on `pc.CHECK_BREEDS` (plague monks, savages and, from build 4, the covered elites), where its own stagger maths disagrees with the client's (`host check …`): it runs `DamageUtils.calculate_stagger_player` as the skipped `stagger_ai` would have, without applying the result, puts back the shield's `blocked_previous_attack`, and compares the stagger type with the client's `pc_stagger`, `pc_kill` or silence for that hit. The stats count both. When that maths says the enemy's attack ignores the stagger by restarting its wind-up (an elite's `reset_attack`, `damage_utils.lua:3565`), the host resets the attack as the skipped `stagger_ai` would have (`host_attack_reset`), since the client sends nothing for a stagger its enemy ignores. For every hit on `pc.CHECK_BREEDS` it also logs what its stagger maths used (D45, `pc.stagger_inputs` in `Shared.lua`): the hit's power and other inputs, the attacker's and the enemy's buffs, and the enemy's stagger state and action, as `host check maths …` for a client's hits and `host own maths …` for the hits it decides itself.
  - Client (`Client.lua`): turns its copy of the enemy every frame by the game's own rules, judges at its damage frame, plays its own block at once, and answers. A frenzy step (family B) is judged at its `anim_cb_frenzy_damage` with the step's block cost, and turns by the combo's rules: it tracks the player the whole step, and on the player's first dodge during the step aims where they were for the breed's `dodge_timer` and turns at 2 instead of 20; once the player has dodged during the step, the reach and cone are the tightened ones, as on the host. A blocked frenzy step plays no recoil and no push. A combo's next step starts turning from where the last one left the enemy facing. A swing is cut, and answered `cut`, the moment the host's change of that enemy's animation (almost always a stagger) reaches the client before its damage frame, the moment the player's own push lands on it (for enemies the client doesn't decide reactions for), or the moment the client shows its own stagger, kill or recoil of that enemy. A push taken on the enemy's shield doesn't cut the swing. An elite's sweep or overhead (family C) is judged at its `anim_cb_damage` with the game's box (`pc.geometry.elite_box`), by the game's own overlap where that finds this player's own hit boxes (checked once per player unit), else by shape (an upright cylinder against the box); only the attacked player's screen turns the enemy, tracking until the attack's `rotation_time` (`rotation_time_step` for a step attack) and stopping for good on a dodge; a hit or a block shows its damage or blocked damage and its push at once (`HitResults.box`). An elite's shove (family D) is judged at `anim_cb_stormvermin_push` with the reach and cone, never tightened, turning towards the player the whole time, and shows its damage and knockback at once (`HitResults.shove`). An elite's attack reset (one of its `reset_attack_animations`) doesn't cut the swing. Keeping in touch: VMF's hook on `PlayerManager.remove_player` drops the host from a client's list of VMF users whenever the host removes a bot (bots share the host's peer id), after which nothing this client sends reaches the host (the build 3.2 playtest). So while a host that has replied in this mission stays quiet, the client asks VMF to ping every player again (`get_mod("VMF").ping_vmf_users`) every `pc.REPING_INTERVAL` (3 s), and says in chat when contact goes and when it comes back.
  - Client (`Reactions.lua`): works out every hit the player sends on `pc.REACTION_BREEDS` with the game's own maths: the damage first (`DamageUtils.calculate_damage` and the game's client-side predicted damage, which the game's projectile code has already recorded for its own hits), then the stagger (`DamageUtils.calculate_stagger_player`, called with a stand-in for the host's blackboard). For a shielded enemy the game's own stagger code runs with a stand-in shield as well, because the client's copy of the shield has no `shield_broken` or `set_is_blocking`; the stand-in learns of shield breaks from the client's own hits and from the host's `rpc_ai_drop_single_item`. A breed's stagger and recoil actions are found through its behaviour tree (`BreedBehaviors[breed.behavior]`), because they aren't always filed under the breed's own name in `BreedActions` (slave rats keep theirs under `skaven_slave_rat`). The stand-in also keeps the attack the enemy is in, which the game's `action_ignores_stagger` reads (a frenzying monk or savage ignores light staggers): from the host's swings at this player, and for other targets from the host's animations, mapped to attacks through the behaviour tree. It keeps the combo's `aborted` flag too, set when a stagger stops a frenzy and cleared when a frenzy starts, because the monk's and the savage's stagger code reads it, and the enemy's health share, which the shielded stormvermin's reads. While the game's stagger maths runs, the stand-in's `action` is the attack the enemy is in, as the host's blackboard has it, unless it is staggered (the counter-push trait's bonus reads it, `damage_utils.lua:641`; T11). Before the game's stagger code runs here, the stand-in shield starts from the host's synced shield (`get_is_blocking`). A stagger that ends a recoil (this screen's own, or one the host played that nothing has ended yet) does what `BTBlockedAction.leave` does first: the recoil's `blocked` flag goes, the stagger count is at least 3 and the shield goes up. The stand-in's stagger ends with whatever the host plays after that stagger's idle (`stagger_finished`, or the event the breed's enter function returned instead: the shielded stormvermin's idle after every stagger, `to_sword` after a shielded clan rat's or marauder's shield breaks, `bt_stagger_action.lua:226`), and as soon as the host refuses or never plays this screen's stagger. A stagger `AiUtils.stagger` refuses (an enemy already blown back) shows nothing, but goes to the host with an empty animation, for its on-stagger procs (D57 review). A stagger the client shows at the very start of a frenzy, before it has seen the frenzy begin, counts (D41). Everything kept per enemy is matched on its network id, because the game reuses a dead enemy's unit for a new one (`BreedFreezer`). For the specials (build 5), the stand-in also learns the attacks whose `ignore_staggers` an animation doesn't show: the packmaster's pull, drag and hoist and the gutter runner's pin from the held player's status (`special_attack`), the leech's grab likewise (`corruptor_grab_stagger`, which picks its `grabbing_stagger_anims`), the ratling gunner's shooting from its first aim (`attack_shoot_align`), `attack_shoot_start` and `rpc_ai_weapon_shoot_start`, the warpfire thrower's from its first turn towards its target (its `attack_anims`: `turn_left`, `turn_right`, `turn_bwd`) and `attack_shoot_start`, each over at any other animation from the host (the warpfire's `attack_shoot_end`), a stagger, or the ratling's `rpc_ai_weapon_shoot_end` (which a realign's `attack_shoot_align` starts again), and the globadier's suicide run from `suicide_run_start` and its detonation from `attack_foff_self`, both kept until it dies, because the host keeps them through its staggers (`shooting_of`, `track_host_animation`). During the run only explosion staggers land. A stagger the player's hit gives a globadier whose detonation has begun is sent as usual, but this screen shows the globadier's death instead, as the host's death message would (no killer, damage source `suicide`, straight down; `detonation_death`), because the host's behaviour tree kills it rather than staggering it. With the debug log on, the client logs what its stagger maths used for every hit on plague monks and savages (`client check maths …`, D45), with the enemy's network id (`go=`), to compare with the host's line for the same hit. A kill plays at once through the game's own client death path. A stagger plays at once with its animation and its root-motion movement on the navmesh. After a block, the recoil plays at once (`/pingcomp recoil full` also moves the enemy). The host's copy of the reaction (the echo) is dropped, and the host's other animation changes for that enemy are held back until the echo arrives, because the host sent them before it applied this reaction. If the host refuses, or no echo comes within 1.5 s (3 s for a blast's stagger), the newest change held back is played. After the echo the screen keeps the enemy's position until the host's reaction ends. The host's voice lines for an enemy (`rpc_play_dialogue_event`, `rpc_interrupt_dialogue_event`) are dropped once it has died on this screen, and for any unit whose dialogue extension this client no longer has, because the game's handler indexes that extension unchecked (build 3: a client crashed on a plague monk's line, `dialogue_system.lua:1760`).
  - Both (`Blasts.lua`, D37): a blast the player sets off reaches the host in one of two ways. Most go as `rpc_create_explosion`, whichever code sends it; right after sending it (`NetworkTransmit.send_rpc_server`), the client works the blast out with the message's own values. A projectile's blast (a bomb, a fireball) sends no message: each machine sets off its own copy when its copy of the projectile lands, so the client works it out when its own projectile's blast goes off (`PlayerProjectileUnitExtension.do_aoe`, with `aoe_data` as the template), and the host notes it when its copy of that projectile lands (`PlayerProjectileHuskExtension.do_aoe`), where the real blast is. Either way the client runs its own copy of the host branch of `DamageUtils.create_explosion`: radius and power (with the player's radius buffs), the units it reaches (an overlap, then line-of-sight rays for blasts that want them), nearest first, and per enemy the distance, power level, hit zone and shield block. It sends `pc_blast` with the network ids of the covered enemies it reaches, split into parts of at most 300 characters (VMF allows 500 for all of a message's values, `mod_manager.lua:626`), then decides each enemy as `AreaDamageSystem._damage_unit` would on the host (the damage, which may kill, then the stagger, with the shield block) through the same code as a hit (`Reactions.blast_hit`). The blast's staggers go as `pc_blast_staggers`, as many to a message as fit in 450 characters, without positions (the host doesn't move enemies for a blast); a stagger whose animation or damage profile has no `NetworkLookup` id goes as `pc_stagger`. Kills go as `pc_kill`.   - `pc_swing_answer` — client to host at its damage frame: `version, id, frame, result, multiplier, improved, direction, through_block, distance, angle, recoil_anim, has_position, x, y, z, yaw`. `result` is `hit`, `blocked`, `miss`, `cut` (the swing never reached its damage frame on the client's screen) or `unjudged` (the client couldn't find the enemy or the attack). `multiplier, improved, direction` are the block values from `can_block`. `distance` and `angle` are only for the host's debug log. `recoil_anim` is the recoil the client played after a block, or empty if it left the recoil to the host; with `has_position`, `x, y, z, yaw` are where its screen showed the enemy.
  - `pc_stagger` — client to host after its hit staggers an enemy: `version, id, go_id, stagger_type, duration, length, dir_x, dir_y, dir_z, anim_scale, stagger_value, always_stagger, is_push, anim, yaw, x, y, z, has_position, damage_profile, target_index, damage_source`. The first values are what `AiUtils.stagger` takes; `anim_scale` is -1 for none. `anim` and `yaw` are the animation and facing the client played, `x, y, z` where it saw the enemy. An empty `anim` is a stagger the game refused on the client's screen, which shows nothing and only runs the hit's on-stagger procs on the host. `damage_profile`, `target_index` and `damage_source` are for the host's `on_stagger` procs.
  - `pc_kill` — client to host after its hit kills an enemy on its screen: `version, id, go_id, hit_zone, damage_type, dir_x, dir_y, dir_z, damage_source`.
  - `pc_blast` — client to host right after a blast of its own goes off (it sent `rpc_create_explosion`, or its projectile's blast went off): `version, blast_id, part, parts, template_name, x, y, z, projectile_go_id, go_ids`. `blast_id` counts this client's blasts; a long list goes in `parts` messages (at most 20), numbered by `part`, and the host waits for all of them. `x, y, z` is the blast's position; `projectile_go_id` the network id of the projectile that set it off, 0 for an explosion message; `go_ids` the network ids of the covered enemies the client decides for that blast, comma-separated, at most 300 characters per part (empty if none). Its staggers follow as `pc_blast_staggers`, its kills as `pc_kill`.
  - `pc_blast_staggers` — client to host after a blast of its own, for the staggers it decided: `version, damage_source`, then 15 numbers per stagger (at most 20 staggers, and only as many as fit in 450 characters): `id, go_id, stagger_type, duration, length, dir_x, dir_y, dir_z, anim_scale, stagger_value, flags, anim, yaw, damage_profile, target_index`. `flags` is 1 for `always_stagger` plus 2 for `is_push`; `anim` and `damage_profile` are `NetworkLookup.anims` and `NetworkLookup.damage_profiles` ids. There is no position: the host doesn't move enemies for a blast's stagger. Each is applied and acknowledged as a `pc_stagger`.
  - `pc_reaction_ack` — host to client for every predicted stagger and recoil, every hook, grab or pounce a client's screen said landed, and every vortex catch: `version, kind, id, result`. `kind` is `stagger` (with the client's id), `recoil` or `grab` (with the swing id), or `catch` (with the vortex's network id); `result` is `applied` or `rejected`. A rejected `grab` or `catch` is undone on the client.
  - `pc_aim` — host to the targeted client when a ratling gunner's stream starts at them (`stream`) or an archer starts aiming at them (`arrow`), and to every modded player when a warpfire thrower starts firing, or turns to a new target while it fires (`jet`): `version, go_id, kind, node_name, target_go_id, aimed`. `go_id` is the shooter's network id, `node_name` the node the host aims a stream at (empty for the others), `target_go_id` the attack's target's network id, and `aimed` whether that is this player (always true for `stream` and `arrow`).
  - `pc_arrow` — host to every modded client for each archer's arrow whose hit roll lets it hit players: `version, go_id, id, aimed, sx, sy, sz`. `id` is the arrow's light-weight projectile id, `aimed` whether this player is its target, and `sx, sy, sz` its spread as a direction in the aim's own frame.
  - `pc_shots` — client to host, several shots judged on its screen to a message, at most every 0.1 s: `version, list`. `list` is entries `kind,go_id,result,zone,source` joined with `;` (at most 12, and 450 characters): `kind` `b` (bullet) or `a` (arrow), `go_id` the shooter's network id, `result` `h` (hit) or `k` (blocked), `zone` the hit zone, `source` the shooter's breed name.
  - `pc_area` — client to host when an area's damage reaches its player, or its player steps into or out of a ground fire: `version, kind, go_id, inside`. `kind` is `tick` (one damage tick: a gas cloud's, or of the ground fire's or the jet's burning, D58), `impact` (a gas cloud's impact), `fire` (stepping into or out of a ground fire), `jet` (a jet's hit, which starts its burning) or `vortex` (a catch); `go_id` the cloud's, the ground fire's, the thrower's or the vortex's network id (a tick's is its source's: the cloud, the fire or the thrower); `inside` true or false (always true but for `fire`).
- Version-report messages (these don't carry `VERSION`, so changing them doesn't need a bump). `/pingcomp version` runs for whoever types it, on host or client, and only they see the list. Anyone who doesn't answer within 3 seconds is listed as `Mod not found.`, which includes players with the mod disabled or on a build older than this command.
  - `pc_version_request` — from the player who typed the command to every other modded player: `request_id`.
  - `pc_version_reply` — back to that player: `request_id, version, fingerprint` (the fingerprint from 2.1 on; older builds don't send it).
- Build stamp: game Lua can't run git, so `build.bat` writes the commit and branch to `scripts/mods/Ping Compensation/BuildInfo.lua` (gitignored) before compiling and deletes it afterwards. `-dirty` after the commit means the build had uncommitted changes. A build made without `build.bat` reports `unknown`.

## Commands
Run this from this folder.
- Build: `./build.bat < /dev/null` in Git Bash, or `.\build.bat` in PowerShell. Use this rather than calling `vmb build` directly, because it also writes the commit and branch that `/pingcomp version` reports. The output is saved to `build_log.txt`. Steam puts the last Workshop upload back over the Workshop folder whenever the game launches, so build while the game is running and reload with Ctrl+Shift+R: a build made before launching is undone (2026-11-16: a solo test ran 3.2 instead of build 4). Check that `/pingcomp version` shows the build's stamp before testing.
- Handout PDF: `./handout_pdf.bat < /dev/null` in Git Bash, or `.\handout_pdf.bat` in PowerShell. It turns `Docs/Briefs/playtest-handout.md` into `Docs/Briefs/playtest-handout.pdf` (gitignored) with `Docs/handout_to_html.py` and headless Edge or Chrome. It needs Python 3 and installs nothing. The converter only understands the Markdown the handout uses, so check the PDF after adding anything new to the handout, such as nested lists or images.
- Timings: `py Docs/rebuild_timings.py [options] <log> [<log> ...]` (`python` if there is no `py`), with every host and client log that has readings; each log's side is worked out from its lines. It rebuilds `DEFAULTS` in `Timings.lua` from scratch from the logs' `[PingComp] timing` lines and the host's recoil-end lines, for every enemy (D47), shares stagger lengths between enemies whose shared ones all agree, writes stagger animations whose readings split as `false`, takes a recoil timing's biggest group of readings, the longer on a tie, after dropping readings under half of what the same recoil takes after the other attacks (D51), and prints what it shipped, what it left out and why (its docstring has the rules). A reading that names its speed counts only at normal speed. `--normal-speed <log>`: a log without speeds whose readings were all at normal speed (the 3.1 logs); in other logs without speeds, only an animation's lowest group of readings counts. `--no-host-cues <log>` leaves out a host log's recoil cues (the 2.1 and 2.2 hosts timed some from the wrong start). Recoil timings ship per attack when the attacks differ. `--dry-run` only prints. A log given to a flag must be given as a log too. `--handout Docs/Briefs/playtest-handout.md` writes the tally into the handout, between its tally lines (then rebuild the PDF); `--source` is the decompiled breed files it counts from (the reference repo by default). The 3.2 rebuild used every log in `TestLogs/` from 2.1 to the calibration session, with `--no-host-cues` for the 2.1 and 2.2 host logs and `--normal-speed` for both 3.1 logs and the build 3.1 calibration log (`TestLogs/2026-11-14-calibration/console-2026-11-14-00.21.27-…`); logs from 3.2 on name their speeds and need neither. Build 4's rebuild (D51) added Lance's two solo logs in `TestLogs/2026-11-16-solo/`: add each new playtest folder's `*.log` to the same command.
- Stagger speed-ups: `py Docs/stagger_speedups.py <host log> <client log>`. From one session: how many of that client's staggers each speed-up limit cuts at the logged ping and at 100 ms more, the speed they need, and how far the client's copy was from the host's when it handed each enemy back. With several clients, add `--from <name>`, the client's in-game name as the host's log writes it.

## Playtest logs
- Lance's own logs are in the game's `console_logs` folder (newest file = last session). Search them for `[PingComp]`.
- Logs sent in by other testers go in `TestLogs/` in this folder, which is gitignored because console logs contain Steam names and IDs. Read them from there. One subfolder per session keeps host and client logs together.
- A client line starts `[PingComp] client swing=` and a host line `[PingComp] host swing=`. The same swing has the same number in both logs, so a host log and a client log from one session can be matched line by line. `[PingComp] MARK` lines are testers' notes, and `[PingComp] ERROR` lines are caught errors.
- Before building on top of a playtested build, go through the brief's checklist for its logs (now "Checking the build 4 playtest", which carries over 3.2's open items).
