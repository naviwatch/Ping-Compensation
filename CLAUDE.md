# Ping Compensation

The Ping Compensation mod for Vermintide 2. This folder is its own git repo, cloned into Vermintide Mod Builder's (VMB) `mods` folder as `Ping Compensation`: the folder name must match `Ping Compensation.mod`, or VMB can't build it. If your VMB folder has its own `CLAUDE.md`, two levels up, its rules apply here too: if they aren't in your context, read that file before doing anything else.

## Design (keep this current)
The full design, its numbered decisions, the roadmap and the deferred work are in [Docs/Briefs/client-authoritative-melee.md](Docs/Briefs/client-authoritative-melee.md). Read it before changing anything. The tester handout is [Docs/Briefs/playtest-handout.md](Docs/Briefs/playtest-handout.md); update it whenever a build changes what testers see or should test. Testers get it as a PDF, so rebuild `Docs/Briefs/playtest-handout.pdf` with `handout_pdf.bat` after every change to it.

- Goal: client-authoritative enemy melee, and the player's own effect on enemies shown on their own screen at once. A swing aimed at a remote player is judged on that player's own screen, on the frame their copy of the enemy fires the damage animation event, from their live position, block and dodge. What the player's own hits and blocks do to an enemy is decided on their screen too. The host books whatever the client reports and never second-guesses it. It is PvE, so game feel beats fairness.
- Built so far: roadmap steps 1 and 2, family A only. Family A is every attack run by `BTAttackAction` whose damage frame goes through the generic `anim_cb_damage`: slave rats, clan rats, marauders, fanatics, gors, ungors, and the non-frenzy swings of monks and savages. Frenzy combos, elite sweeps, overheads and shoves are vanilla until their steps land. Monsters and lords (`breed.boss`) are always vanilla for now. Step 2, with D31 and D32 on top, was playtested on 2026-11-12, and build 2.1 (its fixes, Deathwish and the enemy-data check for D34, and shipped timings for D35) later the same day. Build 2.2 (the 2.1 playtest's fixes: recoils ended early by a leftover cue, cleaned timings, the enemy-data warning's timing) is with the testers, not yet playtested. Decided for the build after its playtest's review, not built yet: explosions and area skills decided on the client (D37), a 3× stagger speed-up limit with a log of the speed each stagger really reached (D38), and `recoil anim` by default (D39).
- Runs on: both.
  - Host (`Host.lua`): announces each swing to its target when the attack starts, with the crowd scaling of its damage, skips its own hit test at its damage frame, and books the client's answer. A hit is booked with `AiUtils.damage_target`, so the unmodified damage code still runs. A block is shown to the other players and makes the enemy recoil.
  - Host (`HostReactions.lua`): applies the reactions a client decided. For every hit a modded client sends (melee, pushes, ranged, career skills) on an enemy in `pc.REACTION_BREEDS` (slave rats, clan rats and marauders with or without shields, fanatics, gors, ungors), it books the damage as usual but skips its own stagger, and applies the client's `pc_stagger` instead, with the client's animation (from any of that enemy's stagger lists) and facing. For a hit taken on a shield it still records the block on the shield, as the skipped stagger maths would have. A client's stagger ends one round trip early (D32): the host plays it faster through the `stagger_scale` animation variable, up to `pc.MAX_STAGGER_SPEEDUP` (1.5×), and past that, or for ungors, whose staggers have no speed variable, ends it early on its timer; its timer is shortened by the round trip as well. The animation lengths this needs come from `Timings.lua` (see below); a stagger whose animation has no length yet only gets its timer shortened. A recoil after a client's block plays the animation the client chose. Both start where the client saw the enemy: the host moves its copy there first if that is within 2.5 m, on the navmesh and on the same floor (D27). A predicted recoil ends one ping early (D14): like vanilla it waits for both its timer and its animation's cue (`anim_cb_blocked_cooldown`), but both are counted from the host's own damage frame. The cue's time into each recoil animation comes from `Timings.lua`; once it is known, the cue flag is held off until that time, whatever set it, and set then. Until an animation's cue is known, the host waits for the animation's own cue. Only `BTBlockedAction.leave` clears the flag, and a recoil ended before its animation's cue still gets that cue afterwards, so at the start of every recoil, of any enemy, a flag left over from an earlier one is cleared. The host measures cue times only from its own recoils, which start at the damage frame as in vanilla, and for those it makes vanilla's random animation pick itself so it knows which one plays. A client's recoil starts when its answer arrives, and its cue can then come much later (marauders: 1.65 s instead of 0.95 s), so it isn't measured there; clients measure their own. If a client says its hit killed (`pc_kill`) and the enemy is still alive here 0.15 s later, the host kills it, credited to that player. Every predicted stagger and recoil is acknowledged (`pc_reaction_ack`). With the debug log on, a stagger the host skipped for a client's hit that no client stagger or kill followed within a second is logged.
  - Client (`Client.lua`): turns its copy of the enemy every frame by the game's own rules, judges at its damage frame, plays its own block at once, and answers. A swing is cut, and answered `cut`, the moment the host's change of that enemy's animation (almost always a stagger) reaches the client before its damage frame, the moment the player's own push lands on it (for enemies the client doesn't decide reactions for), or the moment the client shows its own stagger, kill or recoil of that enemy. A push taken on the enemy's shield doesn't cut the swing.
  - Client (`Reactions.lua`): works out every hit the player sends on `pc.REACTION_BREEDS` with the game's own maths: the damage first (`DamageUtils.calculate_damage` and the game's client-side predicted damage, which the game's projectile code has already recorded for its own hits), then the stagger (`DamageUtils.calculate_stagger_player`, called with a stand-in for the host's blackboard). For a shielded enemy the game's own stagger code runs with a stand-in shield as well, because the client's copy of the shield has no `shield_broken` or `set_is_blocking`; the stand-in learns of shield breaks from the client's own hits and from the host's `rpc_ai_drop_single_item`. A breed's stagger and recoil actions are found through its behaviour tree (`BreedBehaviors[breed.behavior]`), because they aren't always filed under the breed's own name in `BreedActions` (slave rats keep theirs under `skaven_slave_rat`). Everything kept per enemy is matched on its network id, because the game reuses a dead enemy's unit for a new one (`BreedFreezer`). A kill plays at once through the game's own client death path. A stagger plays at once with its animation and its root-motion movement on the navmesh. After a block, the recoil plays at once (`/pingcomp recoil full` also moves the enemy). The host's copy of the reaction (the echo) is dropped, and the host's other animation changes for that enemy are held back until the echo arrives, because the host sent them before it applied this reaction. If the host refuses, or no echo comes within 1.5 s, the newest change held back is played. After the echo the screen keeps the enemy's position until the host's reaction ends.
  - Client (`HitResults.lua`): a hit on the player runs the game's own client code for a hit at once (`PlayerUnitHealthExtension.add_damage`: damage indicator, flinch, rumble, sound), applies the knockback, and shows an HP estimate on the HUD only; the host's copies of the damage and knockback messages are dropped. A blocked swing's push is applied at once the same way. Going down and dying stay with the host.
  - Timings (`Timings.lua`, D35): stagger animation lengths (start to `anim_cb_push_finished`, at normal speed) and recoil cue times (start to `anim_cb_blocked_cooldown`), per breed and animation. They are fixed properties of each animation, so they ship with the mod in `DEFAULTS`, the median of each animation's readings in the playtest logs, and every machine keeps measuring: the host from its own staggers and from its own recoils (not a client's), a client from what its copy of each enemy plays. A reading under 0.3 s, or under half the value already known, is ignored: it is an earlier animation's callback arriving just after a new one started. A machine's own measurements are kept with `mod:set("stagger_lengths_2")` and `mod:set("recoil_cues_2")` and win over the defaults; builds before 2.2 saved polluted readings under `stagger_lengths` and `recoil_cues`, which are no longer read. `/pingcomp timings` writes everything known to the console log in the form `DEFAULTS` uses. After a playtest, rebuild `DEFAULTS` from the individual readings in the logs with `Docs/rebuild_timings.py` (see Commands) rather than from those averages.
  - Difficulty mods (`Compat.lua`, D34): the client's maths reads its own copy of the enemy data, so it must be the host's. Deathwish from "Cata 3 & Deathwish" (Workshop 1835393505, VMF mod `catas`) changes the host's tables only in Adventure, so the host reports which mirrored difficulty mods it has on in its hello reply, and a client running the same mod switches its own copy on or off to match, with that mod's own `start` and `stop`; it switches it off again when it hosts or the mod is disabled. On top, both sides fingerprint the enemy data the client's maths reads (the covered and family A breeds' stagger, health, armour and reach fields; the listed fields of their attack, recoil and stagger actions; `DifficultySettings`; the stagger tables). The client's hits are decided on its screen only while the host says the client's fingerprint is its own: from the first hello that differs, that client's hits are decided on the host until they match, and if they still differ after 3 seconds (`compat.WARN_AFTER`), both get a chat warning saying what differs. The wait covers a difficulty mod switched on one side, which takes a hello or two to be mirrored. The fingerprint is worked out again whenever this machine's mirrored difficulty mods change, so the host's reply never pairs its toggles with an older fingerprint. Recoils and hit results are still shown at once.
  - Dodges: the client applies the weapon's dodge count by default (`/pingcomp dodgecount on`), as the game always has for the host's own hero. In vanilla the host's copy of a remote player never counts dodges (the counter only runs on the player's own machine), so every dodge a client makes counts as effective; `dodgecount off` gives that behaviour.
  - Only remote human players whose client has said hello in the last 4 seconds are judged this way, and the host decides that player's hits itself unless the hello says `attacks` is on. The client shows nothing early unless the host answered a hello in the last 4 seconds, so a modded client with a vanilla or different host stays vanilla. Bots, the host's own hero and players without the mod stay vanilla. Host and client must have the same `VERSION` (in `Shared.lua`).
- Not shown early yet: staggers and kills on elites, specials and bosses, and from explosions, area damage (bombs, fireball blasts, the Mercenary's shout and other area skills) and damage over time, which the host works out itself (D33). They come from the host a ping late, as in vanilla.
- Silence is never a hit. The host books nothing until an answer arrives, and every answer counts for the 5 seconds the host remembers a swing. If a client's hello has expired by the host's damage frame, the host judges that one swing itself. A kill is honoured whatever the hello says, because the enemy is already dead on that player's screen.
- Not copied from vanilla: the host's line-of-sight flag, which only a few breeds have (ungor archers, bestigors); a client-judged swing ignores it. For a client-decided stagger, the client knows the enemy's existing stagger only from what its own screen showed, and the client's result becomes the truth (D26).
- Safety net: every `mod:hook` handler runs everything except the original call through `pc.guard`, which catches errors. After 5 errors in one place the mod sets `pc.broken`: clients stop saying hello and showing anything early, the host stops announcing, and the game carries on with vanilla rules until the next mission.
- Settings: none, only the on/off toggle (`is_togglable`). Chat commands, all under `/pingcomp`, in any capitalisation. Every command typed is written to the console log, and an unknown word is named back to the player. `attack` is accepted for `attacks` and `dodge` for `dodgecount`, and a switch typed on the side where it does nothing (a client switch on the host, or `stagger` on a client) says so. What `stats`, `version` and the switches print also goes to the console log, because some players' VMF settings send echoes to chat only.
  - `version` lists the build each connected player is running, and whether their enemy data matches yours (builds from 2.1 on).
  - `timings` writes every stagger length and recoil cue time this machine knows to the console log, marking the shipped defaults, in the form `DEFAULTS` in `Timings.lua` uses.
  - `debug on|off` writes one line per judged swing, stagger, kill, recoil and timing measurement to the console log, prefixed `[PingComp]`, including the player's dodge state at the damage frame. It is on by default while `PLAYTEST_BUILD` in `Shared.lua` is true (set it false for a public release), and once a player sets it, their choice is saved (`mod:set("debug")`). Host lines name players by their in-game name, not their peer id (which is their Steam id).
  - `echo on|off` (host, off by default): the host's disagreements and unanswered swings also show in chat.
  - When a mission or the keep ends, and when the game closes (VMF's `on_unload`), the stats and, if any were measured, the timings are written to the console log (not the chat), as a fallback for players who don't type `stats` and `timings`; the commands work as before. The game closing straight after a mission doesn't write the same stats again, and a summary written as the game closes reports the side this machine played in its last mission. A game killed with Alt+F4 skips it, but the debug log already holds every event.
  - `stats` prints totals since the mission started.
  - `attacks on|off` (client, on by default): the player's melee hits and pushes decide staggers and kills on `pc.REACTION_BREEDS`. Off leaves them to the host, as in step 1. Changing it sends a hello at once.
  - `recoil off|anim|full` (client, `full` by default): the enemy's recoil after the player's block. `full` plays it and its movement at once; `anim` plays the animation at once and leaves the movement to the host; `off` waits for the host, as in step 1.
  - `predict on|off` (client, on by default): a hit on the player shows its feedback, knockback and HP drop at once.
  - `stagger speed|end|off` (host, `speed` by default): how the host shortens a stagger a client caused (D32). `speed` plays it faster, then ends it early past the limit; `end` only ends it early, cutting its animation short for everyone else; `off` leaves it its full length, as in step 2 before D32.
  - `facing on|off` switches the client-driven facing, to compare. Off means the hit test uses the host's facing as the client sees it, which trails behind the player, so off is far more forgiving than vanilla (first playtest: 7 of 7 swings missed with it off, 5 of which the host would have landed). It is not "the normal game".
  - `dodgecount on|off` applies or ignores the weapon's dodge count for the client. On by default.
  - `mark <note>` writes a marker line to the console log.
- Network messages (bump `VERSION` when any of these change):
  - `pc_hello` — client to host every second, and at once when `attacks` changes or its enemy data has changed: `version, attacks, fingerprint`.
  - `pc_hello_reply` — host to that client, for every hello: `version, fingerprint, toggles, matched`. `fingerprint` is the host's, `toggles` the mirrored difficulty mods it has on (comma-separated keys, `deathwish`), `matched` whether the fingerprint in that hello was the host's. Without a reply in the last 4 seconds the client shows nothing early.
  - `pc_swing_begin` — host to the targeted client when an attack starts: `version, id, attacker_go_id, family, set_name, action_name, attack_anim, box_up, box_down, box_flat, damage_scale`. `family` is `"A"`. `set_name` and `action_name` find the attack in the client's own `BreedActions`. The three box numbers are only used by attacks flagged `use_box_range`, which no attack in the current game data is. `damage_scale` is the crowd scaling of the attack's damage (`diminishing_damage`), for the client's HP estimate.
  - `pc_swing_answer` — client to host at its damage frame: `version, id, frame, result, multiplier, improved, direction, through_block, distance, angle, recoil_anim, has_position, x, y, z, yaw`. `result` is `hit`, `blocked`, `miss`, `cut` (the swing never reached its damage frame on the client's screen) or `unjudged` (the client couldn't find the enemy or the attack). `multiplier, improved, direction` are the block values from `can_block`. `distance` and `angle` are only for the host's debug log. `recoil_anim` is the recoil the client played after a block, or empty if it left the recoil to the host; with `has_position`, `x, y, z, yaw` are where its screen showed the enemy.
  - `pc_stagger` — client to host after its hit staggers an enemy: `version, id, go_id, stagger_type, duration, length, dir_x, dir_y, dir_z, anim_scale, stagger_value, always_stagger, is_push, anim, yaw, x, y, z, has_position, damage_profile, target_index, damage_source`. The first values are what `AiUtils.stagger` takes; `anim_scale` is -1 for none. `anim` and `yaw` are the animation and facing the client played, `x, y, z` where it saw the enemy. `damage_profile`, `target_index` and `damage_source` are for the host's `on_stagger` procs.
  - `pc_kill` — client to host after its hit kills an enemy on its screen: `version, id, go_id, hit_zone, damage_type, dir_x, dir_y, dir_z, damage_source`.
  - `pc_reaction_ack` — host to client for every predicted stagger and recoil: `version, kind, id, result`. `kind` is `stagger` (with the client's id) or `recoil` (with the swing id); `result` is `applied` or `rejected`.
- Version-report messages (these don't carry `VERSION`, so changing them doesn't need a bump). `/pingcomp version` runs for whoever types it, on host or client, and only they see the list. Anyone who doesn't answer within 3 seconds is listed as `Mod not found.`, which includes players with the mod disabled or on a build older than this command.
  - `pc_version_request` — from the player who typed the command to every other modded player: `request_id`.
  - `pc_version_reply` — back to that player: `request_id, version, fingerprint` (the fingerprint from 2.1 on; older builds don't send it).
- Build stamp: game Lua can't run git, so `build.bat` writes the commit and branch to `scripts/mods/Ping Compensation/BuildInfo.lua` (gitignored) before compiling and deletes it afterwards. `-dirty` after the commit means the build had uncommitted changes. A build made without `build.bat` reports `unknown`.

## Hooks
One line per hook, so they can be checked after game patches:
`Class.method` — file:line in the decompiled source — hook type — why.

Line numbers are from the [decompiled source](https://github.com/Aussiemon/Vermintide-2-Source-Code) at `93dea911` (game version 6.13.0).

- `AnimationSystem.animation_callback` — `scripts/entity_system/systems/animation/animation_system.lua:54` — `hook` — The core of the mod, in `Ping Compensation.lua`. ## Commands
Run this from this folder.
- Build: `./build.bat < /dev/null` in Git Bash, or `.\build.bat` in PowerShell. Use this rather than calling `vmb build` directly, because it also writes the commit and branch that `/pingcomp version` reports. The output is saved to `build_log.txt`.
- Handout PDF: `./handout_pdf.bat < /dev/null` in Git Bash, or `.\handout_pdf.bat` in PowerShell. It turns `Docs/Briefs/playtest-handout.md` into `Docs/Briefs/playtest-handout.pdf` (gitignored) with `Docs/handout_to_html.py` and headless Edge or Chrome. It needs Python 3 and installs nothing. The converter only understands the Markdown the handout uses, so check the PDF after adding anything new to the handout, such as nested lists or images.
- Timings: `py Docs/rebuild_timings.py --host <host log> --client <client log>` (either can be given more than once; `python` if there is no `py`). It rebuilds `DEFAULTS` in `Timings.lua` from the logs' `[PingComp] timing` lines, for the breeds in `pc.REACTION_BREEDS`, counting the current defaults as earlier readings, and prints what changed. `--dry-run` only prints; logs from builds before 2.2 need `--no-host-cues`.
- Stagger speed-ups: `py Docs/stagger_speedups.py <host log> <client log>`. From one session: how many of that client's staggers each speed-up limit cuts at the logged ping and at 100 ms more, the speed they need, and how far the client's copy was from the host's when it handed each enemy back. With several clients, add `--from <name>`, the client's in-game name as the host's log writes it.

## Playtest logs
- Lance's own logs are in the game's `console_logs` folder (newest file = last session). Search them for `[PingComp]`.
- Logs sent in by other testers go in `TestLogs/` in this folder, which is gitignored because console logs contain Steam names and IDs. Read them from there. One subfolder per session keeps host and client logs together.
- A client line starts `[PingComp] client swing=` and a host line `[PingComp] host swing=`. The same swing has the same number in both logs, so a host log and a client log from one session can be matched line by line. `[PingComp] MARK` lines are testers' notes, and `[PingComp] ERROR` lines are caught errors.
- Before building on top of a playtested build, go through the brief's checklist for its logs (now "Checking the step 2.2 playtest").
